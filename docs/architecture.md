## Deepgram Nova-3 streaming extension (STT-001B)

The selectable Deepgram provider is an **optional cloud infrastructure adapter** behind the application-owned STT contracts. The capture window still sends PCM16 mono/16 kHz to the authorized FastAPI WebSocket on loopback. Only FastAPI opens a TLS WebSocket to Deepgram; React/Electron do not receive an API Key or contact Deepgram directly. The local defaults and Vosk/Faster-Whisper adapters remain available. A selected provider is bound to the single-use Live grant; no automatic switching or fallback is permitted.

Deepgram interim transcripts (`is_final=false`) are emitted as **replaceable partial UI text**. Segment finals (`is_final=true`) must be accumulated; a completed utterance (`speech_final=true`) is the boundary for question extraction, RAG and optional LLM generation. Neither an interim hypothesis nor a segment final alone authorizes an AI suggestion. Existing bounded PCM flow, send serialization, question deduplication, connection cancellation and stop/cleanup policies must be preserved.

Deepgram resolves `COPILOT_DEEPGRAM_API_KEY` from the backend environment for each new session, then Windows Credential Manager when no environment override exists. Invalid overrides fail explicitly. Settings invokes a native helper without sending keys through React or Electron. Availability checks establish local configuration only, not authorization, billing or reachability. The user must separately select cloud STT and explicitly consent to off-device audio transmission. Provider-side processing and retention depend on Deepgram's terms/settings; no **local** audio recording is not a promise of no remote processing. Cloud use may incur costs.

Windows English system-audio capture, interim/final transcripts and React relay have been observed by the owner; this does not yet validate end-to-end latency, Spanish, realistic conferencing, connectivity failure recovery or production packaging. See [Live Mode observations](live-mode.md) and [roadmap tasks](roadmap.md).

Remaining provider and metering tasks are tracked in the [roadmap](roadmap.md).

### CLOUD-001 — Windows credential boundary

- `infrastructure/windows_credentials.py` owns the concrete Credential Manager adapter and a fixed per-user file-handle guard, independent of `COPILOT_DATA_DIR`. `SHGetFolderPathW` locates `%LOCALAPPDATA%\InterviewCopilot\security\deepgram.lock`; it contains no secret. Generic credentials persist for this user on this computer, not as a roaming or machine-wide credential.
- `deepgram_credentials_helper.py` runs through a fixed development Python path with `-I`, no shell, bounded status-only output and no credential in arguments. Its generic Windows dialog has a locked non-secret username and an initially empty masked password field. CredUI automatic persistence is disabled; the adapter alone writes the fixed application target. Native buffers are cleared; immutable Python strings cannot be reliably erased.
- `electron/credentials.cjs` owns the child lifetime, output allowlist, timeout, stdin cancellation and window recovery. The helper watches Electron's explicit PID, not a potentially intermediate venv launcher. Forced termination closes stdin as well as killing the launcher. Window recovery toggles enabled state off/on because CredUI can alter native state behind Electron's cache. Existing trusted-frame IPC checks permit only enumerated actions and no caller-selected path/target.
- Capture uses shared read handles; mutation uses an exclusive read/write handle on the same file. Integrated capture and both standalone labs acquire before granting loopback media and hold until window close. Every backend Live WebSocket also acquires before processing the handshake and retains its shared lease through provider/generation teardown. This lets a capture window coexist with its backend, while blocking mutations for every provider. OS errors fail closed; process exit releases handles. A lost native lease closes its capture window. Conflicts do not terminate healthy capture.
- The backend reads credentials only for new cloud sessions; it does not hot-swap an open upstream connection. Read-only status exposes configuration/source/error categories, never values, suffixes or hashes. There are no HTTP credential-management endpoints or named pipes. The file guard coordinates cooperating processes; it is not authentication or protection from same-user malware or direct external Credential Manager edits.

Management and native capture remain Windows development-only. Operation/acceptance evidence lives in [Live Mode](live-mode.md#cloud-001--windows-key-management); operational guidance lives in [setup](setup.md#optional-deepgram-nova-3).

## Current implementation

```text
Main Electron window (React, no media permissions)
    ├── Live page: start/stop capture window
    ├── Live page: transcript + Q&A cards with source
    ├── Knowledge Base / Practice / manual query
    └── restricted preload bridge (open/close/status/events)

Second Electron window (separate, nonpersistent session)
    ├── direct user click + explicit consent
    ├── reused standalone getDisplayMedia loopback path
    ├── AudioWorklet → mono PCM16 @16kHz
    ├── provider/language-bound single-use-token local WebSocket → FastAPI/STT
    └── validated text/status/suggestion IPC → main window

FastAPI localhost:8765
    ├── local Vosk (default) / CPU Faster-Whisper EN/ES via /live/transcribe
    ├── heuristic conversational question extraction
    ├── exact Q&A → optional semantic FastEmbed candidates in SQLite
    ├── answer + provenance, or explicit no-evidence
    └── final no-evidence + explicit opt-in → async local Ollama → separate AI suggestion
```

### Module responsibilities today

- `apps/api/app/main.py`: application composition (including one optional generation service), HTTP schemas/routes, upload handling and origin/host restrictions. Session finish suppresses/drains that session's generation before returning its existing report.
- `live.py`: token lifecycle, single active transcription slot, heuristic EN/ES detector, deduplication, WebSocket protocol and retrieval coordination. Grants bind provider and language; stable Vosk partials permit early exact lookup, finals permit exact/semantic lookup. Legacy speech symbols are re-exported for compatibility.
- `application/stt.py`: framework-independent speech result/session/provider contracts, bounded energy segmentation and connection-scoped receive/inference pump. No RAG, LLM or native imports; transport supplies the existing retrieval/event callback. Separate reception and processing bound slow downstream work too.
- `infrastructure/vosk.py`: the existing lazy, locked Vosk cache and unchanged partial/final/word-timing parsing, plus an async session that drains native thread calls on cancellation. `infrastructure/faster_whisper.py` / `whisper_worker.py`: CPU INT8 local-only subprocess adapter/protocol; one language-bound worker per connection, bounded messages/deadlines, explicit terminate/drain/reap on stop/disconnect.
- `domain/knowledge.py`: framework-independent frozen `ParsedEntry` dataclass, shared by parsing and persistence (ARCH-003).
- `domain/text.py`: the existing mutable `STOPWORDS` set, shared directly by persistence and retrieval (ARCH-004). Both legacy module imports reference this same object; its content is unchanged. `textnorm.py` remains unchanged and pure.
- `application/ports.py`: `RetrievalReader`, a structural Protocol exposing only `find_exact_qa` and `find_matches` (ARCH-005). It preserves existing dictionary rows and requires no framework or concrete storage implementation.
- `application/generation.py`: independent `GenerationService`, typed `GenerationProvider` port, concise localized EN/ES instructions and three immutable synthetic style demonstrations per language (AI-001C), bounded deadline/input/output and immutable AI-generated provenance with no documentary source (AI-001A). Examples cover a technical concept, architecture/trade-off and a second-person behavioral answer structure without fabricated personal facts. Its small, standard-library content check rejects substantial fixed-instruction copying and narrowly recognized unsupported autobiographical work claims before attaching provenance. No HTTP/framework dependency or retrieval change.
- `infrastructure/ollama.py`: local-only non-streaming chat HTTP adapter using runtime `httpx`; no proxies, redirects, retries, credentials, tools or model pulls. Builds fresh system → three selected-language user/assistant example pairs → current user question messages; no actual conversation history. Validates bounded completed assistant output; provider payloads are not exposed as error messages.
- `bootstrap.py`: optional generation, Whisper and Deepgram provider composition, called by `main.py` without model loading/network I/O. Invalid optional generation configuration degrades to an unconfigured service with no provider, retaining the safe `not_configured` reason rather than conflating it with intentional disablement. Configuration and limits are documented in [setup](setup.md).
- `live_generation.py`: connection-scoped generation coordinator, outside the PCM/Vosk loop (AI-001B). One active call and one replaceable latest pending question; revisions plus session/connection/question IDs suppress stale results. Replacement, stop, disconnect, error and HTTP session finish invalidate/cancel work. All WS event sends share a lock; generation failures preserve no-evidence and do not terminate capture. Request cancellation cannot guarantee instant termination of Ollama's internal inference.

AI-001D adds only the outbound `generation_failed` event: `session_id`, `question_id` and an allowlisted existing `GenerationError` code (`disabled`, `not_configured`, `invalid_input`, `unavailable`, `timeout`, `invalid_response`, `provider_error`). The coordinator now schedules disabled/unconfigured outcomes through the existing bounded worker; service checks return the reason before any provider invocation. Failed and successful outcomes share session-open, revision, close and send-lock guards. Cancellation is not converted into a failure, and failures while sending/disconnected do not trigger another send or log private exceptions. Existing generation prompts, model/timeout/output settings, safety validation and retry behavior are unchanged.

The isolated capture script relays this event without treating it as an STT error, and suppresses it after Stop or capture-attempt/socket replacement. Electron validates its trusted sender/frame/origin, bounds correlation IDs, rejects unknown codes/mixed answer provenance and forwards only the four allowlisted fields. Bounded memory-only history/replay includes the event. React attaches the localized reason to the matching retained `no_evidence` card, including an older superseded question when a valid late outcome arrives. Unmatched/evicted cards, stopped/interrupted outcomes and cards with a received AI answer do not acquire a new failure label. Updating a card consumes no additional queue slot and does not alter transcription or audio phase. Provider-side generation replacement still suppresses obsolete sends; the renderer does not infer cancellation acknowledgements or create orphan answers.
- `parsers.py`: format-specific extraction into Q&A or text fragments, with source locations and resource limits. Re-exports the same Domain `ParsedEntry` class for compatibility.
- `store.py`: local document files, SQLite schema, entries, FTS5, vectors and Live/Practice session persistence. Imports `ParsedEntry` directly from Domain, not from the document parsers.
- `retrieval.py`: exact and manual lexical retrieval, Live retrieval policy, plus existing lexical Practice assessment/reporting. Storage type dependencies use `RetrievalReader`; this module no longer imports `KnowledgeStore`.
- `semantic.py`: optional local FastEmbed model, explicit incremental indexing, similarity/margin abstention and stored-answer candidates.
- `semantic_indexing.py`: one lazily started, process-owned indexing thread for explicitly requested background work. The API lifespan rejects new work and drains it on shutdown; SQLite stores per-document/model progress, not a generic job queue. Index writers serialize separately from the model lock; background batches contain at most four missing questions and defer between batches while `LiveRuntime.connection_active` is true. The accessor only reads the existing Live slot; it does not change capture/STT behavior.
- `apps/desktop/src/App.tsx`: shell and existing Overview/Knowledge/Practice/Settings pages; `api.ts`/`types.ts`: HTTP client and shared TypeScript contracts. `features/live/LiveWorkspace.tsx` owns read-only Live presentation, bridge subscriptions, capture-window open/close and the existing manual search. `liveState.ts` is a small presentation-only state transition/replay module, not a transport or STT abstraction. `LiveSuggestion.tsx` keeps the four provenance categories explicit.
- `electron/main.cjs`: windows, permissions, protection, sender validation, IPC sanitization and bounded event history. Preloads expose narrow bridges.
- `audio-lab/transcribe.js` and `pcm-processor.js`: consent-driven capture, Web Audio lifecycle, PCM conversion, local HTTP/WS and lab display. The integration reuses these files rather than a rewritten capture engine.

ARCH-003 originally extracted the shared five-field record. Bilingual XLSX support adds optional `language=None` while retaining five-argument construction, frozen equality and existing public imports. Domain uses only the standard library; persistence no longer loads PDF/Office libraries through its entry type. This is an incremental boundary, not a fully layered Clean Architecture backend or a feature-separated desktop.

ARCH-004 moved stopwords out of persistence without changing filtering behavior. ARCH-005 replaces retrieval's concrete storage type dependency with the application read port; `KnowledgeStore` implements it structurally without inheritance, wrappers or SQL changes. Existing functions, dictionaries, exact/lexical/semantic priorities, scores, thresholds and Practice feedback remain unchanged. Other modules still use concrete adapters; application/infrastructure separation is not complete.

STT-001A introduces only speech contracts and a bounded pump, not a general streaming framework. The Vosk adapter is moved (public `app.live` imports retained), not redesigned; recognition calls/timings and retrieval policies are preserved. New CPU work stays behind the application-owned speech port. `LiveRuntime` retains legacy Vosk composition defaults for compatibility; main/bootstrap explicitly compose the new optional adapter. Transport owns authentication and event translation, not segmentation/native inference.

Whisper deliberately uses a subprocess rather than a cancelled `to_thread` future: native CTranslate2 inference cannot reliably be interrupted by cancelling its Python awaiter, and the approved Whisper runtime is isolated from the working API `.venv`. A subprocess makes normal teardown terminable/reapable, at the cost of a model reload on each session and Windows subprocess-capable loop requirements. No persistent worker pool or new service is introduced. Vosk's existing short native calls are drained rather than abandoned. Receive/worker limits are documented in [setup](setup.md#optional-faster-whisper-live-setup-stt-001a); backpressure fails closed without silent audio loss or provider changes. The energy gate is a minimal dependency-free endpointing choice, not robust VAD or a claim of real conversational accuracy. Forced cuts remain transcript/documentary-only, without Ollama generation or misleading EOS measurements. The ≤3 s p95 criterion needs actual Windows/human acceptance, not just paced synthetic replay.

### Documents, retrieval and consistency

See [document limitations](setup.md#documents-and-retrieval) for extraction by format. A supported import is not a promise of Q&A extraction: PDF fragments, for example, are not Live answer candidates.

- Manual `POST /answers`: normalized exact Q&A first, then FTS5 candidates with lexical scoring for similar Q&A/excerpts. Similar Q&A must share a question-topic term after removing stopwords and fixed generic EN/ES request wording; their similarity/coverage scores use those question terms, not answer-only hits or generic question framing. FTS still searches all existing fields, the 0.30 cutoff and score weights remain unchanged, and excerpt scoring is unchanged. This is a conservative lexical gate, not semantic understanding or synonym inference. The manual Live text box uses this same endpoint, not semantic Live retrieval.
- Automatic Live: normalized exact Q&A first, then optional semantic Q&A; otherwise `no_evidence`. Semantic is a possible stored answer to review, not verified truth. Only after final no-evidence, an enabled/configured local service may generate a separately labeled suggestion. Missing/unavailable semantic candidates also return no evidence; algorithms and priorities are unchanged. Partials and stop-flush finals never trigger generation.
- DET-003 cleans only Live question candidates in `live.py`, not transcripts or shared `textnorm.normalize`. Partial/final paths share one bounded leading-introduction helper; a fixed whole-candidate EN/ES set excludes standalone greetings/audio checks without substring/topic/speaker classification. New harmless introductions are stripped only before a recognizable request (or an exact excluded check). Context, negation and programming-language distinctions remain. Final-boundary suffix recognition retains its previous rules so numbers in technical questions are not mistaken for enumeration boundaries. Dedupe remains before generation supersession, with unchanged per-connection TTL/capacity: ignored or equivalent repeated candidates do not retrieve/cancel; genuine new accepted questions still invalidate older work. See [focused evidence and limits](live-mode.md#det-003--conservative-greetings-and-introduction-dedupe).
- Import stores original files, extracted entries and FTS rows. Extraction normalizes whitespace and limits field length; main-window IPC additionally limits answer length. Do not promise byte-for-byte original formatting or unlimited answers.
- Bilingual XLSX pairing groups question/answer columns by matching explicit language, retaining sheet/row/columns/language for each complete row pair. `domain/language.py` provides conservative EN/ES query eligibility independently of UI/STT language. Exact/FTS Q&A are filtered in SQLite and at retrieval boundaries; explicit matching labels outrank legacy exact/manual candidates without bypassing topical relevance. Semantic candidates are language-filtered before the existing score/margin policy; no translation, provider change or generated documentary wording occurs. Nullable `entries.language` is an additive migration; legacy rows remain unlabelled, with only clear question-language mismatches excluded. Unknown legacy answer language is not certified. Fragments and Practice retain their existing behavior. See [limits and non-destructive reimport](setup.md#bilingual-evidence-and-safe-legacy-xlsx-reimport).
- For normalized exact questions only, an unambiguous declared source language overrides the request-word heuristic. Labelled ES/EN collisions require an identifiable query language or abstain. Approximate/semantic language eligibility and topical safeguards are unchanged. This handles original questions phrased outside the heuristic vocabulary, without introducing another classifier or translating evidence.
- `bilingual_reprocess.py` and the standalone `reprocess_bilingual_xlsx.py` command implement a deliberately offline, format-specific repair, not a generic migration/API framework. They validate the stored original's hash, eight row-4 headers, unique IDs and 257 complete pairs per language. Read-only preview fingerprints affected entries/vectors/Practice state. Confirmed apply checks that fingerprint under `BEGIN IMMEDIATE`, backs up SQLite and the original, preserves every matched entry ID and all source wording/vector bytes, completes language/location metadata, and adds only missing pairs/FTS rows. Changed/unmatched existing content aborts instead of remapping or deleting Practice history. Only the affected document's stale semantic status marker is reset to unrequested derived readiness; no index/model work is initiated. The backend must be stopped; the CLI requires explicit confirmation and rejects a listener on 8765. Existing document-scoped RAG-002 actions then embed missing questions only.
- Embeddings cover Q&A questions only. Indexing remains manual by default; `COPILOT_AUTO_SEMANTIC_INDEX=1` (or `true`) opts new imports into cached-model background indexing after import commits. Existing documents are not swept automatically. Parsing/import persistence runs off the API event loop, and semantic failure does not roll back files, entries or FTS. Live retrieval never initiates indexing or downloads.
- Deletion removes entries/FTS/vectors, semantic status and linked Practice answers. Index batch writes atomically skip deleted entries and never overwrite existing vectors; status writes select only surviving documents. SQLite deletion/in-flight-index races have deterministic coverage; filesystem and SQLite changes are still not one atomic transaction. No in-place document update API exists.

**RAG-002 implementation:** `/semantic/status` retains its counts/model/policy and adds `automatic_enabled`, `worker_active`, `deferred_for_live` and per-document counts, pending/indexing/completed/failed state, requested-work flag and allowlisted error. `semantic_index_state` is an additive table keyed by document/model with cascading deletion; readiness derives from actual vectors, including indexes created before this feature. Interrupted pending/running work becomes failed/interrupted on startup or graceful shutdown and requires explicit retry; download consent is never stored. `/semantic/index` retains synchronous manual indexing and explicit `allow_download`; optional `document_id` and `background:true` scope/schedule work. Background requests reject downloads. Knowledge Base reuses EN/ES notice styles, shows the actual enabled/disabled/unconfirmed setting and per-document Index/Retry actions, and aborts bounded status polling when unmounted. A timed-out request may still be scheduled; refresh before retrying. Native embedding already in progress cannot be forcibly cancelled; shutdown drains it and background work defers at the next batch boundary if Live begins. No new dependency/service, retrieval policy/threshold change or real-model latency guarantee. See [scope](roadmap.md#rag-002--automatic-incremental-semantic-indexing) and [evidence/Windows limits](live-mode.md#rag-002--automatic-incremental-semantic-indexing).

### Permission, transport and privacy boundaries

Main Electron session explicitly denies display/microphone capture. The separate nonpersistent `live-capture` partition permits a display request only from its trusted main frame with a user gesture. Consent is checked in the capture UI and required for the backend token request. Capture includes **all Windows output**, not one app. Video is required by the loopback request but is not displayed or recorded.

The capture page uses Vite `http://127.0.0.1:5173`; PCM16 mono at 16 kHz goes directly to `ws://127.0.0.1:8765/live/transcribe`. Tokens are ephemeral, single-use, provider/language/session-bound and sent in the start message. Selection is immutable within a connection, not a client-side instruction to change the active recognizer. WS validates Origin/Host independently of HTTP CORS. HTTP allows development origins and requests without Origin; these controls do not authenticate other local processes. Packaged capture is disabled pending separate bootstrap/authentication/origin validation; do not allow `file://`/`null` origins as a shortcut.

IPC checks the window/frame/URL and allowlists bounded text/status/suggestion/metric fields; raw audio and credentials are not relayed. Live transcripts and audio are not persisted. Main-process history is capped at 80 durable events. React retains up to 80 finalized transcript fragments and 20 question cards, each with one documentary payload and at most one correlated AI payload, plus one replaceable interim string. Both panels have their own bounded-height scroll region. On mount, a bounded 160-packet bootstrap buffer merges the existing snapshot with overlapping in-flight events; it does not add IPC fields or persist history. Navigating away discards local presentation state; returning can restore only the native 80-event snapshot, potentially fewer than 20 complete cards. The auxiliary lab DOM still accumulates results until reset. SQLite persists documents, vectors and session metadata; basic Practice also persists submitted answers.

Live phase/provider labels interpret the existing capture status text; provider remains unknown until a recognized engine status is received. This avoids labeling cloud STT as local without changing selection/grant contracts. Audio stopped and capture-window closed are separate facts: the UI checks the existing native window state after an ambiguous stop event. Opening a fresh window resets local history before IPC; showing existing controls does not. Stop/error removes obsolete interim presentation while preserving previous finals and answers, including the existing documentary final flush. The UI does not invent an LLM-progress event or change cancellation/retrieval behavior. Status wording changes must keep these presentation mappings in sync. Equal final text is not globally deduplicated: repeated words can be distinct utterances. Snapshot overlap matching is bounded/best-effort under the existing ID-free transcript contract, not a new exactly-once delivery guarantee.

The integrated auxiliary window defaults to 560 × 720 px, with a 490 × 520 px minimum. Native disclosures hide PCM diagnostics and duplicate auxiliary feeds without removing the DOM IDs used by `transcribe.js`. Auxiliary CSS is scoped to the transcription page, not the raw-audio lab. Capture consent, permissions, origin checks and protection policies remain at the existing native boundaries. Main-window layout is described below and in the [visual reference](../DESIGN.md).

### UI-003 — capture presentation and interface locale

The isolated nonpersistent capture renderer still owns consent, the real Start click, media tracks, AudioContext/AudioWorklet and HTTP/WS/STT lifecycle. After matching backend readiness, worklet initialization/connection and a running audio context, it publishes a narrowly enumerated internal `capture_state` with a positive safe-integer attempt revision. Main validates the existing capture sender/frame/URL, rejects obsolete/invalid transitions and keeps these notifications out of the existing React Live packet history. Existing audio/transcript/suggestion payloads and backend contracts are unchanged.

During active integrated Windows capture, main creates a native `Tray` with a local bitmap waveform and restore-workspace/show-controls/stop actions **before** calling `setSkipTaskbar(true)` on both windows and `hide()` on the auxiliary. The main workspace remains visible; tray click restores it from minimization. Showing controls reuses the auxiliary and does not restart audio. Its explicit hide action is trusted-capture-only and allowed only during a healthy active attempt. If tray creation fails, normal taskbar access and visible controls remain. No global shortcut, native package or new service is introduced. Closing the main window closes the auxiliary so hidden capture cannot keep running alone.

Only the auxiliary disables `backgroundThrottling`. PCM progress notifications now also originate from the existing worklet callback, independent of `requestAnimationFrame`. One main-process interval, bounded to active presentation, restores both taskbar buttons and controls if advancing PCM has not been reported for more than six seconds (checked every two seconds). A nonrunning audio context or capture-renderer crash also restores access. Recovery disables rehide for that attempt without trying to restart providers or silently reconnect. Stop, error, close and app exit release the interval/tray and restore taskbar behavior for surviving windows. Progress proves only client-side PCM sending, not successful STT/network consumption; OS suspension, shell/tray behavior and hidden audio continuity need real Windows acceptance. Auxiliary `hide()` never closes/reloads it; normal close/stop teardown and provider-specific final-flush/cancellation semantics remain.

`src/i18n.tsx` owns the main React locale context and a single `copilot.ui-language` localStorage preference (`en`/`es`, Spanish fallback, storage failure stays memory-only with a warning). `public/ui-language.js` is a shared pure phrase/template dictionary loaded locally by both pages; `public/audio-lab/capture-ui.js` updates only the auxiliary's initially authored text/attributes and explicitly marked operational labels. Incoming content is not walked or translated. Main forwards the allowlisted locale through a dedicated validated IPC setter; the capture bridge can read/subscribe without acquiring persistence or generic IPC access. Initial locale reads cannot overwrite a newer change. Native tray copy follows the same preference. Locale updates never remount Live, alter consent or selection locks, or touch STT grants/provider/language, Ollama prompts/configuration, retrieval, sources, document content or transcripts. Known backend-authored Practice warnings are translated only for display; unknown external errors remain original. Canonical Spanish Live status strings remain unchanged internally, so `liveState.ts` interpretation/replay does not depend on the displayed locale. Standalone transcription remains Spanish by default and has no native hide controls without the integration bridge. Packaged capture remains disabled.

AI-001B adds `generated_suggestion` with `kind:ai_generated`, `session_id`, connection-scoped `question_id`, detected `question`, `language`, bounded `answer`, `provider:ollama`, configured `model` and `source:null`. Documentary final suggestion events retain their contract plus additive correlation IDs. Generated events have no documentary `status`/`match_type`; IPC rejects mixed provenance, invalid fields and untrusted senders. React renders AI text separately with a review warning and no documentary attribution. Only the detected question/language plus fixed instructions and selected-language synthetic style examples reach loopback Ollama; no full transcript/real history/documents/audio, tools or credentials. Nothing generated is stored in SQLite or persistent application logs. Ollama must be separately configured for local-only operation; fixed prompts cannot guarantee model compliance or factuality.

AI-001C changes fixed prompt content and adapter message assembly; its approved remediation also adds a conservative application-owned output policy. Existing service/provider signatures, provenance, settings, output/deadline bounds and Live lifecycle remain unchanged. The policy compares normalized 12-word spans against fixed instructions and checks a bounded set of first-person past-work patterns with professional context. Matching standalone declarative facts in the question may support those claims; this does not verify the user's facts. Rejection raises only the existing sanitized `invalid_response`, without retries, replacement generation, logging or transport changes. The policy does not classify general question intent, change DET/STT or guarantee factuality. Indirect stories/paraphrases can escape it, and valid personal paraphrases can be rejected.

Deterministic review confirmed false positives for numeric-word/synonym paraphrases of supplied facts and for a hypothetical label in a preceding sentence. The approved test cleanup preserves this runtime policy rather than adding semantic matching or another validation layer. Lexical cases exercise the application policy directly; representative service and Live integration tests protect rejection propagation, no retries, audio continuity and teardown. Adapter and evaluator tests retain their distinct transport, security and resource boundaries. See [known false-positive examples](live-mode.md#ai-001c--test-cleanup-and-known-false-positives).

`apps/api/eval_ollama.py` is a separately invoked synthetic evaluation utility, not application composition, a public endpoint or a runtime prompt switch. Its evaluation-only transport freezes baseline messages and observes bounded allowlisted metrics while retaining production validation/cancellation. Both arms share current content validation. On explicit `--show-answers`, it retains bounded synthetic rejected answers for false-positive review; these never pass through a production event/error. It requires the existing exact `qwen3:1.7b` tag, never installs/pulls/unloads/configures a model, and writes no files. See [evidence and outstanding acceptance](live-mode.md#ai-001c--few-shot-generation-evaluation).

### Main-window Live presentation (UI-004)

The shared main topbar stays in normal flow with `position:sticky; top:0`, an opaque mode-matched background and stacking below existing overlays. `App.tsx` measures its actual wrapped height with a cleaned-up `ResizeObserver`; compact Live commands use that height rather than a fixed 56 px offset. A bounded focus guard scrolls the page only when a focused main-area control would sit under the sticky topbar or, while sticky, the compact command header; it ignores controls inside those sticky layers. At ≤360 px effective height the compact command header becomes static so it cannot consume most of the reading area. Layout containment keeps long Live feeds' scroll overflow inside their own scrollports, avoiding page overflow beyond the sticky parent's boundary. Sidebar, native window controls and capture/security boundaries are unchanged.

Compact and expanded layouts reuse the existing main `BrowserWindow`. Trusted main-frame IPC accepts only the two mode names and finite background opacity in [0.8, 1]; translucent settings require Windows support and compact mode. Dedicated minimize/close calls expose no generic native access. Preload remains narrow; main renderer sandbox and capture-permission denial are unchanged.

Main retains separate memory-only normal rectangles, expanded maximization and background opacity. Compact uses a 760 × 520 px default and a 720 × 400 px minimum; expanded keeps its 880 × 650 px minimum. Restoration clamps bounds/minimum size to the matching display work area, including saved compact rectangles smaller than the current minimum. If the work area itself is smaller than a minimum, the effective minimum and bounds shrink to stay visible. No reload, capture-window replacement, provider change or capture lifecycle action occurs on presentation changes. Always-on-top/content protection remain on the same window; tray and continuity timer survive mode changes.

Electron 39 requires a frameless Windows window for transparency and warns about transparent-window resizing. Windows startup therefore creates a transparent-capable, custom-framed main window, initially painted opaque. Compact CSS applies alpha only to dark backgrounds, never `BrowserWindow.setOpacity` or text. Main disables manual resize while translucent. The opaque action restores resizing; native construction/background failures select an opaque fallback. `COPILOT_OPAQUE_WINDOW=1` bypasses transparency at startup and retains the normal native frame. Rendering faults without native exceptions require that explicit fallback. See [Electron limitations](https://github.com/electron/electron/blob/v39.0.0/docs/tutorial/custom-window-styles.md#transparent-windows).

`App.tsx` owns presentation state independently of the mounted Live workspace. `liveState.ts` retains newest-first question cards, not separate result events. A documentary event creates a card; subsequent documentary events with the same session/question IDs update its payload without replacing the key or reordering it. AI and generation failures update only the matching retained no-evidence card. Legacy documentary events without both IDs stay independent; unmatched or evicted AI/failure events cannot create a card. `LiveSuggestion` always renders its documentary question/result and optionally adds the correlated AI section inside that same article; exact/semantic sources are never assigned to AI. Bounds and replay behavior are defined in the privacy section above.

A stable React structure and CSS Grid place expanded transcript left (35%) and the continuous Q&A queue right (65%); compact places the transcript left (38%) and the same queue right (62%), with the Q&A panel first in DOM/keyboard order. There is no separate answer-history disclosure or visible newest-first caption. Both reading feeds are independently bounded and scroll inside their own row. Transcript is an always-visible section with no collapse control in either mode; compact uses one bounded grid row with independent feed scrolling. Minimum-height windows still require page scrolling. Flex sizing replaces the old native disclosure-content height workaround. Final transcript badges are removed only visually; hidden EN/ES prefixes and a separate latest-final polite status retain semantics. Interim text uses a static listening indicator. Transcript replay/deduplication and all STT events stay unchanged.

Existing transport has no question-detected/RAG-start or generation-start/cancelled event. Cards therefore begin at the documentary event, not from speculative transcript classification. Incomplete no-evidence cards show generation start as unconfirmed, and are marked superseded by newer questions. A genuine late result can enrich an older retained card without changing queue position. Stop/error/restart events close incomplete outcomes against obsolete AI while keeping retained cards and failures visible. The existing explicit new-capture workspace reset remains unchanged; this is not cross-session persistence. These are renderer presentation boundaries, not a claim that a model started or acknowledged cancellation. No backend changes or new event fields are required.

The pin reads native state with the existing `getWindowState` before each toggle and displays the confirmed `setAlwaysOnTop` result. Pending interactions are locked; an IPC failure marks confirmation unknown rather than falsely reporting Off. There are no new channels, subscriptions, persistence, transport, retrieval or generation behaviors. Native Windows visual composition and real capture continuity remain pending acceptance.

### Screen-sharing exclusion

The main window calls `setContentProtection(true)` on Windows and exposes a Settings toggle plus always-on-top. Compact overlay mode reuses this main window; it is not a separate protected window or a stronger exclusion mechanism. The integrated capture-controls window and standalone audio lab do not call `setContentProtection` and are not content-protected; main-window protection is not inherited. UI-001 preserves these native policies, the isolated nonpersistent capture partition, trusted-origin/frame/user-gesture checks, and the main renderer's denial of capture permissions. The Live footer reports the native flag as requested/unconfirmed/disabled, not verified invisibility, and the capture HTML warns that its window may be shared.

[Electron content protection](https://www.electronjs.org/docs/latest/api/browser-window#winsetcontentprotectionenable) uses Windows `SetWindowDisplayAffinity` with `WDA_EXCLUDEFROMCAPTURE`. [Microsoft documents](https://learn.microsoft.com/en-us/windows/win32/api/winuser/nf-winuser-setwindowdisplayaffinity) support from Windows 10 version 2004; older versions fall back to `WDA_MONITOR` behavior. Protection depends on supported capture APIs and desktop composition; it is not a security/DRM guarantee. The reported protection flag is not evidence of remote exclusion.

Exclusion while remaining visible locally is a core Live requirement. Teams, Zoom and Google Meet compatibility remains pending real Windows sessions, separately by client/browser version and capture mode. It does not guarantee undetectability, hide the process or replace audio consent. See [manual validation](live-mode.md#screen-sharing-exclusion--manual-acceptance-pending).

## Approved direction — incremental refactoring

Progressively separate backend responsibilities into:

```text
domain/          Pure entities, normalization and business policies
application/     Document, retrieval, indexing and Live use cases; required ports
infrastructure/  SQLite/files, document parsers, Vosk and FastEmbed adapters
presentation/    FastAPI HTTP/WS routes and transport schemas
bootstrap        Configuration and dependency composition
```

Dependencies point inward: domain imports no frameworks/adapters; application depends on domain and only the ports it needs; infrastructure implements those contracts; presentation translates transport to use cases. Composition wires concrete adapters. Keep the `app.main:app` entry point and existing HTTP/WS contracts during migration.

For desktop, progressively separate `src/app`, `src/features/{live,knowledge,practice,settings}` and genuinely shared HTTP/bridge/UI modules. Electron should separate window lifecycle, permission/protection policies, IPC validation/handlers and preloads. Business coordination should not be embedded in JSX or platform handlers. Do not mechanically reproduce backend layers in React.

Exact filenames and extraction order still need task-level approval. Prefer a few cohesive modules, hooks/reducers and concrete required ports over generic repositories, a DI framework, global state dependency or an interface for every class. Preserve the lab and existing Practice behavior; expanded Practice remains future work. The only current generation adapter is local Ollama, now optionally integrated with Live; real provider/Windows acceptance is pending.

Validate main Live first, then extract one responsibility per task with contract/regression tests and Windows acceptance where audio, IPC, lifecycle or protection is affected. Separate behavior fixes from moves. See [roadmap](roadmap.md) and [engineering rules](../AGENTS.md).
